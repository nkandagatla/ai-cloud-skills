Install for your agent

The installer copies the skills, adds the guard and wires it into each agent's hook system where one exists. Agents without hooks get instruction-level guardrails and a check command.

Repo or global, and how to call a skill

Skills load on their own when a request matches their description. You can also call one by name. Full guide: docs/USAGE.md.

Team and infrastructure repos: install per repo

Skills, guard policy and the production list are committed, reviewed in PRs, the same for every developer and every tool, and they work in CI and cloud agents. One install covers Claude Code, Codex, Copilot and Gemini in VS Code because they read the same files.

Your own repos: install globally

install --scope user puts the skills and guard in your home folder for every repo on the machine. Don't also install per repo for the same agent, or skills appear twice. Claude Code users can use the plugin instead (auto-updates).

# A. team repo (recommended): all packs, CI checks, pre-commit, then open a PR
npx github:nkandagatla/ai-cloud-skills install --yes --with-ci --with-precommit
# B. app repo with no cloud: git, languages, databases, AI cost
npx github:nkandagatla/ai-cloud-skills install --packs git,lang,db,ai
# C. AWS infra repo, strict mode, Claude Code + Cursor
npx github:nkandagatla/ai-cloud-skills install --packs aws,git --agents claude,cursor --mode strict
# D. global, just me, every repo on this laptop
npx github:nkandagatla/ai-cloud-skills install --scope user --agents claude,codex

With and without the skills

The same request, with an unguided agent and with this library installed. More in docs/EXAMPLES.md.

"Fix the failing payment test"

WITHOUT

3,000 lines of test output (about 40k tokens) land in context and are re-sent every turn. Then cat .env puts the DB password in the transcript.

WITH

Output trimmed to the failure and summary (about 1k tokens), full log saved. .env read blocked; the skill points to .env.example.

"Delete orders older than 2019"

WITHOUT

One giant DELETE against the prod host: locks, replication lag, no backup.

WITH

Prod write denied. Count, back up, delete in batches with lock_timeout, run via a reviewed script. Unbounded DELETE is blocked everywhere.

"Ship the fix to prod quickly"

WITHOUT

terraform apply -auto-approve; nobody saw a resource would be replaced.

WITH

Blocked. Plan, replacements called out, rollback, PR; the pipeline applies after approval.

"My rebase went wrong, reset everything"

WITHOUT

git reset --hard then git push -f origin main: lost work, overwritten teammates.

WITH

Force-push to main blocked, reset asks first. Backup branch, reflog, push to your branch with --force-with-lease.

"Why can't the pod reach the DB?"

WITHOUT

kubectl get secret db-creds -o yaml, decoded in chat.

WITH

Secret read blocked. Read-only triage: DNS, NetworkPolicy, endpoints, identity, security groups.

"Classify 40,000 tickets overnight"

WITHOUT

Synchronous loop on the top model, a 1,500-token prompt re-sent 40,000 times, rate-limit retries.

WITH

Smallest model that passes a quality check, batch API (about half price), cached prompt prefix, retry only failures.

How the guard decides

Hard rules apply everywhere (cloud, git, databases, shell, publishing). Every other cloud or database CLI call is classified as read, change or destructive, and its target is matched to an environment tier from .cloud-guard/policy.json.

Operationsandboxnonprodunknownprod
Read: describe, list, get, plan, what-if, diffALLOWALLOWALLOWALLOW
Change: create, update, deploy, apply tfplanALLOW strict: askASKASKDENY PR instead
Destructive: delete, terminate, destroy, state rmASKASKASKDENY
Hard rules: public data, 0.0.0.0/0 on admin ports, admin grants, long-lived keys, audit off, key deletion, printing secrets, -auto-approve, editing the guardDENYDENYDENYDENY

Seatbelt, not sandbox

The guard reads command text and file paths. Give the agent read-only credentials by default, and keep SCPs, Azure Policy and Org Policy as the real boundary.

Humans own the policy

Agents cannot edit .cloud-guard/ or hook settings. Weakening a rule needs a written justification in the policy file.

Secrets never enter the transcript

Credential files, state files, secret values and tokens are blocked on read. Secret material is blocked on write.

Everything is audited

Every ask and deny lands in .cloud-guard/audit.jsonl with secrets redacted, so you can review what the agent tried.

Fewer tokens, same history

token-saver trims oversized command output after it runs, keeps errors and summaries, and saves the full log for follow-up reads. Earlier conversation is never rewritten.

See what was guarded and saved

The guard and token saver keep local counters (no command text). report turns them into a summary for you, your PR or your manager.

node .cloud-guard/bin/report.mjs                               # last 30 days, text
node .cloud-guard/bin/report.mjs --price 3 --html report.html  # dashboard with a $ estimate
node .cloud-guard/bin/report.mjs --md                          # paste into a PR, wiki or Slack
node .cloud-guard/bin/report.mjs --dirs ../api,../web,../infra  # one view across repos
node .cloud-guard/bin/report.mjs --json                        # feed a central dashboard
